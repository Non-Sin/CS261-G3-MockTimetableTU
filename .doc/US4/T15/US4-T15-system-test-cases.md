## 1. แนวทางและสภาพแวดล้อม

System test ทดสอบ **ทั้งระบบต่อกันตั้งแต่หน้าเว็บ ผ่าน API ไปถึงฐานข้อมูล** ตามลำดับใน Sequence Diagram ของ US4-T06 ไม่ใช่ทดสอบทีละชั้นเหมือน Unit และ Integration Test

| Flow | ที่มา | สรุป |
| --- | --- | --- |
| 1. Logout | T06 | กด "ออกจากระบบ" → `POST /api/auth/logout` (Bearer, ไม่มี body) → `204` → UI ล้าง authentication state → กลับหน้า Login ถ้า token ใช้ไม่ได้ได้ `401` และ UI ทำผลเหมือนเดิม |
| 2. Session หมดอายุ | T06 | ผู้ใช้ไม่เรียก Logout API ฝั่ง UI พบ `401` จาก API ใดก็ได้ที่ต้อง Authentication → ล้าง state → กลับหน้า Login พร้อมข้อความว่า Session หมดอายุ |

ข้อกำหนดที่ใช้ตาม T06

- US4 **ไม่มี DAO, entity หรือ DB operation ใหม่** Logout และการตรวจ Session หมดอายุไม่อ่านหรือเขียนตารางใดเลย ผลที่ตรวจใน DB จึงเป็น "ไม่เปลี่ยน"
- การล้าง state ฝั่ง Client ทำทั้งกรณี `204` และ `401`
- Session หมดอายุตรวจจากอายุของ token ไม่ต้องอ่าน DB

สภาพแวดล้อม

- รัน frontend, backend (Spring Boot) และฐานข้อมูลทดสอบจริงทั้งชุด
- ตรวจ request/response ด้วย DevTools tab Network และยิง API ตรงด้วย Postman
- **TU Login API จำลอง (stub)** เหมือน US3-T13 เพราะเป็นระบบภายนอก
- **ต้องย่ออายุ token ในสภาพแวดล้อมทดสอบ** (เช่น 1–2 นาที) เพื่อไม่ต้องรอจริง ดูหัวข้อ 3 ข้อ 1

ข้อมูลทดสอบ

| บัญชี | ใช้กับ |
| --- | --- |
| A | CS ภาคปกติ, Active (`6809610000`, Alysa Liu) บัญชีหลัก |
| A2 | CS ภาคปกติ, Active อีกคน ตรวจว่าไม่มีข้อมูลค้างข้ามบัญชี |
| ตารางเรียนของ A | มีวิชาอยู่ในตารางอย่างน้อย 2 วิชา (จาก US1) ใช้ตรวจว่าข้อมูลไม่หายหลัง logout |

## 2. Test Cases

คอลัมน์ผลที่คาดหวังตรวจ 3 ชั้น: **UI** (สิ่งที่เห็นบนหน้าจอ), **API** (request และ response ใน Network), **DB** (ข้อมูลในฐานข้อมูล)

### 2.1 Flow 1: Logout

| ST | สถานการณ์ | ขั้นตอน | ผลที่คาดหวัง | ที่มา |
| --- | --- | --- | --- | --- |
| ST-01 | logout ปกติ | login บัญชี A → เปิดหน้าเมนูหลัก → กด "ออกจากระบบ" | **API** `POST /api/auth/logout` พร้อม `Authorization: Bearer <token>` ไม่มี body ตอบ `204 No Content` **UI** กลับหน้า Login และ token ไม่ค้างในที่เก็บฝั่ง Client **DB** ไม่เปลี่ยน (ไม่มี SQL ใหม่) | T06 |
| ST-02 | กลับไปหน้าเดิมหลัง logout | ต่อจาก ST-01 กดปุ่ม Back ของเบราว์เซอร์ | ไม่แสดงข้อมูลของบัญชี A หน้าที่ต้อง login พากลับหน้า Login (ถ้ามี request ใหม่ต้องได้ `401`) | ข้อเสนอ |
| ST-03 | เข้าหน้าเมนูหลักโดยตรงหลัง logout | ต่อจาก ST-01 พิมพ์ URL หน้าเมนูหลักตรงๆ | ถูกพากลับหน้า Login | ข้อเสนอ |
| ST-04 | login ใหม่หลัง logout | ต่อจาก ST-01 login บัญชี A อีกครั้ง | login สำเร็จด้วย token ใหม่ Navbar แสดง "Alysa Liu" และ "6809610000" | T06 |
| ST-05 | สลับบัญชี | ต่อจาก ST-01 login บัญชี A2 | Navbar แสดงข้อมูลของ A2 ไม่ปนกับ A และไม่เห็นตารางเรียนของ A | ข้อเสนอ |
| ST-06 | ข้อมูลไม่หายหลัง logout | login A → เพิ่มวิชา → logout → login A อีกครั้ง | ตารางเรียนเดิมยังอยู่ครบ **DB** แถวใน `timetable_entry` และ `user` ไม่ถูกลบหรือแก้ | T06 |
| ST-07 | กด logout ซ้ำเร็วๆ | login A → ดับเบิลคลิกปุ่ม "ออกจากระบบ" | UI กลับหน้า Login ปกติ ไม่ขึ้น error (ถ้ามี request ที่สอง อาจได้ `401` ซึ่ง UI ต้องรับได้) | ข้อเสนอ |
| ST-08 | logout ซ้ำจากอีกแท็บ | login A เปิดสองแท็บ → logout แท็บ 1 → กด logout แท็บ 2 | **API** `204` หรือ `401` ตามที่ระบบทำ **UI** แท็บ 2 ล้าง state และกลับหน้า Login ผลเหมือน logout สำเร็จ ไม่ค้างหน้าเดิม | T06 |
| ST-09 | logout ตอน token หมดอายุแล้ว | login A → รอ token หมดอายุ → กด "ออกจากระบบ" | **API** `401` ProblemDetail **UI** ล้าง state และกลับหน้า Login ไม่ค้างหน้าเดิม | T06 |
| ST-10 | ใช้ token เดิมหลัง logout | login A เก็บ token ไว้ → logout → ยิง `GET /api/users/me` ด้วย token เดิมใน Postman | ผลตามที่ทีมตัดสิน: ถ้า JWT เป็นแบบไม่เก็บสถานะ (stateless) token จะยังใช้ได้จนหมดอายุ (`200`) ซึ่งต้องบันทึกเป็นข้อจำกัดใน PR ถ้ามี invalidate ฝั่ง server ต้องได้ `401` ตรวจให้ผลตรงกับที่ตัดสิน | T06, ข้อเสนอ |

### 2.2 Flow 2: Session หมดอายุ (ปล่อยทิ้งไว้จนหมดเวลา)

| ST | สถานการณ์ | ขั้นตอน | ผลที่คาดหวัง | ที่มา |
| --- | --- | --- | --- | --- |
| ST-11 | หมดอายุแล้วใช้งานต่อ | login A → ปล่อยทิ้งจน token หมดอายุ → เปิดหน้าหรือกดฟังก์ชันที่เรียก API (เช่น `GET /api/users/me`) | **API** `401` ProblemDetail ไม่ถึง Controller **UI** ล้าง authentication state กลับหน้า Login พร้อมข้อความว่า Session หมดอายุและต้องเข้าสู่ระบบใหม่ **DB** ไม่เปลี่ยน | T06 |
| ST-12 | หมดอายุแต่ไม่ทำอะไร | login A → ปล่อยทิ้งจน token หมดอายุ โดยไม่กดอะไร | หน้าไม่เปลี่ยนเองจนกว่าจะมี request ถัดไป (UI ตรวจจาก `401` ไม่ได้ตั้งตัวจับเวลา) ตรวจว่าตรงกับที่ออกแบบ | T06, ข้อเสนอ |
| ST-13 | ข้อความ Session หมดอายุต่างจาก logout ปกติ | เปรียบเทียบหน้า Login ที่ได้จาก ST-01 กับ ST-11 | หลัง logout ปกติ **ไม่มี** ข้อความ Session หมดอายุ หลังหมดอายุ **มี** ข้อความนี้ | T06, ข้อเสนอ |
| ST-14 | หมดอายุกลางการทำรายการ | login A (ตารางมี N วิชา) → รอ token หมดอายุ → กดเพิ่มวิชา | **API** `POST /api/timetable/entries` ตอบ `401` **UI** กลับหน้า Login **DB** จำนวนแถวใน `timetable_entry` ยังเท่าเดิม (ไม่มีวิชาถูกเพิ่ม) | T06, ข้อเสนอ |
| ST-15 | หมดอายุแล้ว login ใหม่ | ต่อจาก ST-11 login A อีกครั้ง | login สำเร็จ ตารางเรียนเดิมยังอยู่ครบ | T06 |
| ST-16 | refresh หลังหมดอายุ | login A → รอ token หมดอายุ → refresh หน้า | ได้ `401` จาก API ที่หน้าเรียก แล้วถูกพากลับหน้า Login (ไม่ค้างหน้าว่างหรือโหลดไม่จบ) | ข้อเสนอ |
| ST-17 | ทุก API ที่ต้อง Authentication ปฏิบัติตรงกัน | ยิงด้วย token ที่หมดอายุทีละ endpoint: `GET /api/users/me`, `GET /api/timetable`, `POST /api/timetable/entries`, `DELETE /api/timetable/entries?entryIds=` | ทุกตัวได้ `401` เหมือนกัน และ UI ทุกหน้าตอบสนองเหมือนกัน (ล้าง state กลับหน้า Login) | T06 |
| ST-18 | ขอบเขตเวลา | login A → ก่อน token หมดอายุ 1 นาที เรียก API → หลังหมดอายุเรียก API | ก่อนหมดอายุได้ `200` ปกติ หลังหมดอายุได้ `401` และเวลาหมดอายุตรงกับค่าที่ตั้ง | ข้อเสนอ |
