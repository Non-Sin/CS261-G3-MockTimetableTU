## 1. แนวทาง

Unit test ของ UI ทดสอบ component หน้า login และ Navbar **โดยจำลอง (mock) `authApi.login` และ `userApi.getCurrentUser`** ไม่เรียก backend จริง ตรวจว่า UI แสดงผลและเปลี่ยนหน้าถูกต้องตามคำตอบจากหัวข้อ 2 การเรียก API จริงทั้งสองชั้นอยู่ที่ Integration Test ของ US3

## 2. สัญญาที่ UI ต้องรองรับ (สรุปจาก API Spec)

`POST /api/auth/login` ส่ง `{ username, password }` ตอบ `200 { token }` หรือ error แบบ ProblemDetail พร้อม `code` ที่ UI ใช้สลับหน้า (frontend มี type `AuthErrorDetail`)

| ผลจาก API | HTTP | `code` | หน้าที่ UI ต้องแสดง (Prototype) |
| --- | --- | --- | --- |
| สำเร็จ | 200 | - | พาไปหน้าเมนูหลักทุกครั้ง (ข้อสรุปประชุม) |
| รหัสผิด | 401 | `INVALID_CREDENTIALS` | กล่องแจ้งเตือนในฟอร์ม login |
| บัญชี มธ. ไม่ active | 403 | `ACCOUNT_INACTIVE` | กล่องแจ้งเตือนในฟอร์ม login ว่าบัญชีไม่อยู่ในสถานะใช้งานปกติ (ตาม Sequence Diagram T06) |
| ไม่ใช่ CS ภาคปกติ | 403 | `NOT_CS_STUDENT` | หน้า "ไม่สามารถเข้าใช้งานระบบได้" (Access Denied) |
| ถูกระงับ | 429 | `ACCOUNT_LOCKED` + `retryAfterSeconds` | หน้า "ระงับการเข้าสู่ระบบชั่วคราว" พร้อมตัวนับถอยหลัง |

`GET /api/users/me` (ส่ง `Authorization: Bearer <token>`) ตอบ `200 { studentId, firstName, lastName }` ใช้แสดงที่ Navbar มุมขวาบน

403 มี 2 code ที่ UI ต้องแยกกัน: `ACCOUNT_INACTIVE` แจ้งเตือนในฟอร์ม ส่วน `NOT_CS_STUDENT` ไปหน้า Access Denied

หมายเหตุ: ครั้งที่ 5 ที่ใส่รหัสผิดได้ `429` ทันที (ไม่ใช่ `401`) ตาม Spec ข้อ 3 ของลำดับตรวจ ครั้งที่ 1–4 ได้ `401`
