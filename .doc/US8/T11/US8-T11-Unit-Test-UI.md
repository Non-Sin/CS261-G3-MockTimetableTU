# US8-T11: Design Unit Test Cases ส่วน UI

## User Story

US8: จัดตารางเรียนจำลองตามแผนในเล่มหลักสูตร

## Objective

ออกแบบ Unit Test Cases สำหรับ UI การจัดตารางตามแผนการเรียน โดยยึดชื่อปุ่มและลำดับการทำงานตาม UI Prototype ครอบคลุมการเปิดหน้าต่าง เลือกชั้นปี/ภาคเรียน/แผน/วิชาโท การ preview อัตโนมัติ การเพิ่มลงตาราง การยกเลิก/ปิดหน้าต่าง และการแสดงกรณีวิชาซ้ำหรือเวลาเรียนชน

## Scope

- ปุ่ม `จัดตามแผนหลักสูตร` และการเปิดหน้าต่าง
- รายการแผนและกรณีไม่มีแผน
- ตัวเลือกแผนการศึกษาสำหรับชั้นปีที่ 3–4 และตัวเลือกวิชาโท
- การเรียก preview (`dryRun: true`) อัตโนมัติเมื่อเลือกค่าที่จำเป็นครบ และหัวข้อ `วิชาแนะนำสำหรับ: ...`
- รายการวิชาที่จะเพิ่มและรายการวิชาที่ข้ามพร้อมเหตุผล
- ปุ่ม `เพิ่มลงตารางเรียน`, `ยกเลิก` และปุ่ม `X` ปิดหน้าต่าง
- วิชาที่อยู่ในตารางแล้ว และ dialog แจ้งเตือนเวลาเรียนชน
- สถานะ loading, error และการป้องกันการส่งคำขอซ้ำ

การทดสอบนี้อยู่ระดับ UI โดย mock API และไม่เชื่อมต่อ backend/ฐานข้อมูลจริง ไม่ได้ทดสอบอัลกอริทึมเลือก section หรือการจัดเก็บข้อมูล

## เอกสารอ้างอิงและ Dependency

- US8-T05: [DTO & API Spec](../T05/US8-DTO-API-Spec.md), [DTO Class Diagram](../T05/US8-DTO-Class-Diagram.md), [API Class Diagram](../T05/US8-API-Class-Diagram.md)
- US8-T06: sequence diagram การเลือกแผน, preview และ confirm
- Frontend ใช้ Vitest และ React Testing Library ที่มีอยู่ใน `frontend/package.json`; ไม่เพิ่ม dependency จากงานออกแบบนี้

US8-T05 และ US8-T06 ถูก merge เข้า `develop` แล้ว เอกสารนี้จึงอ้างอิง API contract และ sequence diagram ใน branch ปัจจุบัน สำหรับการตรวจวิชาซ้ำจะทดสอบเฉพาะวิชาที่มีอยู่ในตารางปัจจุบัน (`COURSE_ALREADY_IN_TIMETABLE`) ไม่ทดสอบประวัติวิชาที่เรียนผ่าน เพราะไม่มีข้อมูล transcript ใน API contract ของ US8

## Test Approach

- Render หน้า/ส่วน UI ด้วยข้อมูลทดสอบควบคุมได้
- Mock boundary ของ API ให้คืน `StudyPlanList` และ `ApplyPlanResponse` ตาม US8-T05
- ใช้ user interaction ผ่าน React Testing Library; ตรวจองค์ประกอบด้วย accessible role/name หรือข้อความที่แสดงต่อผู้ใช้
- เมื่อเลือกค่าที่จำเป็นครบ UI เรียก `dryRun: true` เอง ไม่ต้องมีปุ่ม `ดูสรุป`; ใช้ `dryRun: false` เมื่อกด `เพิ่มลงตารางเรียน`
- ตรวจว่า preview ไม่ทำให้ตารางเปลี่ยน และหลังยืนยัน UI ใช้ `timetable` ที่ได้จาก response ของ confirm
- ชื่อ component, route และข้อความ UI ให้ปรับตาม implementation จริง โดยคงพฤติกรรมที่ระบุใน Expected Result
- เอกสารนี้เป็นการออกแบบ test cases เท่านั้น ยังไม่ได้รันทดสอบจริง

## Test Data

| ชุดข้อมูล | รายละเอียด |
|---|---|
| StudyPlanList ปี 2 | `studyYear: 2`, `semester: 1`, มีแผนเดียว `planType: null`, `minors: []` |
| StudyPlanList ปี 3 | มี `SPECIAL_PROJECT` และ `CO_OP`; มีวิชาโทอย่างน้อย 1 รายการใน `minors` |
| Preview ปกติ | `added` มีรายวิชาพร้อม `sectionNo`; `skipped` มีอย่างน้อยหนึ่งรายการพร้อม `reason` และ `message`; `timetable: null` |
| Preview วิชาโท | `added` หรือ `skipped` มีรายการ `source: "MINOR"`; วิชาแผนหลักใช้ `source: "PLAN"` |
| Confirm response | `dryRun: false`, มี `timetable` ที่รวมวิชาใหม่และวิชาเดิม |
| Empty plans | `plans: []`, `minors: []` |
| วิชาซ้ำ | มีวิชาเดียวกันอยู่ในตารางก่อนแล้ว; preview ส่ง `COURSE_ALREADY_IN_TIMETABLE` และ `existingSectionNo` |
| เวลาเรียนชน | `CS301` ชนกับ `RE468` วันจันทร์ 09:30–12:30; UI แสดง conflict alert |
| API error | จำลองการ reject ของการโหลดแผน, preview หรือ confirm |

ข้อมูลใน test เป็น mock ไม่อ้างว่าเป็นข้อมูล seed จริงของฐานข้อมูล

## Test Cases

### [UT-UI-01] เปิดหน้าต่างจัดตารางตามแผน

**Related CoS:** การจัดตารางตามแผนการเรียน

**Preconditions:** หน้า UI พร้อม render และ mock API โหลดแผนได้

**Test Steps:**
1. Render หน้าตารางเรียนจำลอง
2. ตรวจว่ามีปุ่ม `จัดตามแผนหลักสูตร`
3. คลิกปุ่มดังกล่าว

**Expected Result:**
- UI เปิดหน้าต่างจัดตารางตามแผน
- หน้าต่างแสดงตัวเลือกชั้นปีและภาคเรียน
- หน้าต่างมีปุ่ม `ยกเลิก` และปุ่ม `X` สำหรับปิด

### [UT-UI-02] เลือกชั้นปี/ภาคเรียนแล้วโหลดแผนและ preview อัตโนมัติ

**Related CoS:** แสดงวิชาแนะนำตามตัวเลือกของผู้ใช้

**Preconditions:** หน้าต่างจัดตารางตามแผนเปิดอยู่; mock API คืน StudyPlanList ปี 2 ที่มีแผนและ mock apply-plan คืน preview สำเร็จ

**Test Steps:**
1. เลือกชั้นปีที่ 2
2. เลือกภาคเรียนที่ 1
3. รอให้ UI โหลดแผนและสร้าง preview อัตโนมัติ

**Expected Result:**
- UI เรียก API โหลดแผนด้วย `studyYear: 2` และ `semester: 1`
- เมื่อโหลดแผนสำเร็จ UI เรียก `POST /api/timetable/apply-plan` ด้วย `dryRun: true` โดยไม่ต้องกดปุ่ม `ดูสรุป`
- UI แสดงหัวข้อ `วิชาแนะนำสำหรับ: ...` และรายการวิชาตาม preview
- UI แสดงสถานะกำลังโหลดระหว่างรอ response และไม่ส่ง preview ซ้ำจาก selection เดิม

### [UT-UI-03] ไม่มีแผนการเรียนที่ตรงกับตัวเลือก

**Related CoS:** กรณีข้อมูลว่าง

**Preconditions:** หน้าต่างเปิดอยู่; mock API คืน `plans: []` และ `minors: []`

**Test Steps:**
1. เลือกชั้นปีและภาคเรียน
2. รอผลโหลดแผน

**Expected Result:**
- UI แสดงข้อความแจ้งว่ายังไม่มีแผนสำหรับตัวเลือกนั้น
- UI ไม่เรียก apply-plan preview และไม่แสดงรายการวิชาหรือปุ่มเพิ่มที่ต้องอาศัยแผน
- UI ไม่แสดง error สำหรับผลลัพธ์ว่างที่ถูกต้อง

### [UT-UI-04] เลือกแผนการศึกษาสำหรับชั้นปีที่ 3–4 และวิชาโท

**Related CoS:** ตัวเลือกแผนการศึกษาชั้นปีที่ 3–4

**Preconditions:** Mock API คืนแผน `SPECIAL_PROJECT`, `CO_OP` และรายการวิชาโท

**Test Steps:**
1. เลือกชั้นปีที่ 3 และภาคเรียนที่ 1
2. ตรวจตัวเลือกแผนการศึกษาและวิชาโท
3. เลือก `CO_OP` และเลือกวิชาโทหนึ่งรายการ
4. เปลี่ยนเป็นชั้นปีที่ 2

**Expected Result:**
- ปี 3 แสดงตัวเลือกทำหัวข้อพิเศษและสหกิจศึกษา และบังคับให้เลือกแผนก่อนแสดงรายวิชาของแผน
- ตัวเลือกวิชาโทมีค่าเริ่มต้นเป็นไม่เรียนวิชาโท และเลือกได้ไม่เกินหนึ่งรายการ
- เมื่อเลือก `CO_OP` UI แสดงรายวิชาของแผนสหกิจ ไม่ปะปนกับแผนทำหัวข้อพิเศษ
- เมื่อเลือกวิชาโท UI ระบุสถานะ/ชื่อวิชาโทที่เลือก
- เมื่อเลือกค่าที่จำเป็นครบ UI เรียก preview (`dryRun: true`) อัตโนมัติและอัปเดตหัวข้อ `วิชาแนะนำสำหรับ: ...`
- เมื่อเปลี่ยนเป็นปี 2 UI ซ่อนตัวเลือกแผนการศึกษาและวิชาโท และล้าง selection ที่ไม่รองรับสำหรับปี 2

### [UT-UI-05] แสดง preview และเหตุผลที่ข้ามตาม response

**Related CoS:** แสดงวิชาแนะนำอัตโนมัติและรายการที่เพิ่มไม่ได้พร้อมเหตุผล

**Preconditions:** เลือกแผนและภาคเรียนครบ; mock `POST /api/timetable/apply-plan` แบบ preview ให้คืน `dryRun: true`

**Test Data:** `added` มีวิชา `PLAN` พร้อม section; `skipped` มีตัวอย่างเหตุผล `COURSE_ALREADY_IN_TIMETABLE`, `NO_SECTION_AVAILABLE`, `TIME_CONFLICT` และ `CREDIT_LIMIT_EXCEEDED` ตาม response ที่ UI รองรับ

**Test Steps:**
1. เลือกชั้นปี/ภาคเรียน และตัวเลือกแผน/วิชาโทที่จำเป็น
2. รอ preview response ที่ UI เรียกให้อัตโนมัติ
3. ตรวจหัวข้อและรายการวิชาแนะนำ

**Expected Result:**
- UI เรียก apply-plan ด้วย `dryRun: true` และ `planId`, `academicYear` รวมถึง `minorId` เมื่อเลือกวิชาโท
- UI แสดงหัวข้อ `วิชาแนะนำสำหรับ: ...` ให้ตรงกับชั้นปี ภาคเรียน แผน และวิชาโทที่เลือก
- รายการ `added` แสดงข้อมูลวิชาและ section ตาม response
- รายการ `skipped` แสดงวิชาและเหตุผลจาก `message`/`reason` ที่ response ส่งมา
- รายการที่มี `source: "MINOR"` แสดงป้ายบอกว่าเป็นวิชาโท
- Preview ไม่เปลี่ยนตารางที่แสดงอยู่ และไม่แสดง `timetable` สำหรับผล preview

### [UT-UI-06] วิชาที่อยู่ในตารางแล้วต้องไม่ถูกเพิ่มซ้ำ

**Related CoS:** CoS 2 — วิชาที่มีในตารางแล้วต้องไม่ถูกเพิ่มซ้ำ

**Preconditions:** ตารางมี `CS301` อยู่แล้วใน section เดิม; mock preview คืน `CS301` ใน `skipped` ด้วยเหตุผล `COURSE_ALREADY_IN_TIMETABLE` และข้อมูล `existingSectionNo`

**Test Steps:**
1. เปิดหน้าต่าง `จัดตามแผนหลักสูตร` และเลือกแผนที่มี `CS301`
2. รอ preview อัตโนมัติ
3. ตรวจรายการวิชาที่แนะนำและวิชาที่ข้าม
4. กด `เพิ่มลงตารางเรียน` และรอ confirm response

**Expected Result:**
- Preview แสดง `CS301` ในรายการที่ข้าม พร้อมเหตุผลว่าอยู่ในตารางแล้วและ section เดิม
- `CS301` ไม่ปรากฏใน `added` และ UI ไม่แสดงวิชาซ้ำ
- หลัง confirm ตารางยังมี `CS301` เพียงรายการเดียวและ section เดิมไม่เปลี่ยน

### [UT-UI-07] แสดงคำเตือนเมื่อวิชาแนะนำเวลาชนกับวิชาในตาราง

**Related CoS:** CoS 3 — แจ้งเมื่อไม่สามารถเพิ่มวิชาเนื่องจากเวลาชน

**Preconditions:** ตารางมี `RE468` วันจันทร์ 09:30–12:30; แผนที่เลือกมี `CS301` ซึ่งมีเวลาเรียนชนกัน; mock response/state ให้ UI แสดง conflict alert ตาม prototype

**Test Steps:**
1. เปิดหน้าต่าง `จัดตามแผนหลักสูตร` และเลือกแผนที่มี `CS301`
2. เลือกชั้นปี/ภาคเรียนให้ครบและรอ preview อัตโนมัติ
3. ตรวจ dialog แจ้งเวลาเรียนชน
4. กดปุ่ม `ตกลง`

**Expected Result:**
- UI เปิดหน้าต่างแจ้งเตือนข้อความ `ตรวจพบเวลาเรียนซ้อนทับกัน ไม่สามารถเพิ่มได้`
- ข้อความ/รายละเอียดระบุว่า `CS301` ชนกับ `RE468` วันจันทร์ 09:30–12:30
- `CS301` ไม่ถูกเพิ่ม และ `RE468` ที่มีอยู่ยังคงอยู่ในตาราง
- เมื่อกด `ตกลง` หน้าต่างแจ้งเตือนปิดตาม UI Prototype

### [UT-UI-08] ปิดหน้าต่างได้ทั้งปุ่มยกเลิกและปุ่ม X

**Related CoS:** ปุ่ม `ยกเลิก` และปุ่ม `X` ปิดหน้าต่าง

**Preconditions:** หน้าต่างจัดตารางตามแผนเปิดอยู่และมี preview แสดงแล้ว

**Test Steps:**
1. ในรอบแรก กดปุ่ม `ยกเลิก`
2. เปิดหน้าต่างใหม่และทำให้มี preview แสดง
3. ในรอบที่สอง กดปุ่ม `X`

**Expected Result:**
- ทั้ง `ยกเลิก` และ `X` ปิดหน้าต่างได้
- ทั้งสองวิธีไม่เรียก apply-plan แบบ `dryRun: false`
- ตารางและหน่วยกิตไม่เปลี่ยนหลังปิดหน้าต่าง

### [UT-UI-09] แสดงผลเมื่อไม่มีวิชาเพิ่มได้

**Related CoS:** กรณีข้อมูลว่าง/ผลลัพธ์ไม่มีวิชาเพิ่ม

**Preconditions:** Mock preview คืน `added: []` และ `skipped` มีรายการพร้อมเหตุผล

**Test Steps:**
1. เลือกค่าที่จำเป็นให้ UI ขอ preview อัตโนมัติ
2. ตรวจรายการวิชาแนะนำ

**Expected Result:**
- UI แสดงสถานะว่าไม่มีวิชาที่เพิ่มได้ พร้อมรายการที่ถูกข้ามและเหตุผล
- UI ไม่แสดงรายการ `added` ปลอม หรือแสดงจำนวนเพิ่มเป็นค่าที่ไม่ตรงกับ response
- UI จัดการผลลัพธ์ `200` ที่ `added` ว่างได้โดยไม่แสดงข้อผิดพลาดทางเทคนิค

### [UT-UI-10] เพิ่มวิชาลงตารางและแสดงผลจาก response

**Related CoS:** ปุ่ม `เพิ่มลงตารางเรียน`

**Preconditions:** หน้าต่างแสดง preview แล้ว; mock confirm ให้คืน `dryRun: false` และ `timetable` ล่าสุด

**Test Steps:**
1. กดปุ่ม `เพิ่มลงตารางเรียน`
2. รอ confirm response
3. ตรวจตารางและสรุปผลหลังยืนยัน

**Expected Result:**
- UI เรียก apply-plan ด้วยค่าที่เลือกเดิมและ `dryRun: false`
- ระหว่างส่งคำขอ ปุ่ม `เพิ่มลงตารางเรียน` ถูก disable หรือแสดง loading ตามรูปแบบ UI
- เมื่อสำเร็จ UI ปิดหน้าต่างและแสดงตารางจาก `timetable` ใน confirm response
- UI แสดงผลเพิ่ม/ข้ามให้ตรงกับ response ล่าสุด ไม่ใช้ผล preview เก่าทับผลยืนยัน
- การคลิกยืนยันซ้ำระหว่างคำขอกำลังทำงานไม่ส่งคำขอซ้ำ

### [UT-UI-11] จัดการ error ขณะโหลดแผนหรือขอ preview

**Related CoS:** กรณีผิดพลาด

**Preconditions:** Mock API ให้ reject ใน request ที่กำลังทดสอบ

**Test Steps:**
1. ทดสอบกรณีโหลดรายการแผนล้มเหลว
2. ทดสอบกรณีขอ preview ล้มเหลว
3. ตรวจข้อความ error และลองทำรายการใหม่

**Expected Result:**
- UI แสดงข้อความผิดพลาดที่ผู้ใช้เข้าใจได้ ไม่แสดง stack trace
- UI ไม่แสดงรายการ preview เก่าราวกับเป็นผลของ request ใหม่
- UI คงตัวเลือกที่ผู้ใช้ทำไว้เมื่อเหมาะสม และเปิดโอกาสให้ลองใหม่
- เมื่อ retry สำเร็จ UI แสดงผลจาก response ใหม่

### [UT-UI-12] จัดการ error ขณะเพิ่มวิชาลงตาราง

**Related CoS:** กรณีผิดพลาด

**Preconditions:** มี preview; mock confirm request ให้ reject แล้วสามารถ retry ได้

**Test Steps:**
1. กดปุ่ม `เพิ่มลงตารางเรียน` และจำลอง API error
2. ตรวจสถานะตารางและข้อความแจ้งเตือน
3. ลองยืนยันใหม่เมื่อ request พร้อมทำงาน

**Expected Result:**
- UI แจ้งว่าบันทึกไม่สำเร็จ และไม่แสดงตารางใหม่เป็นผลสำเร็จ
- UI ไม่ล้างวิชาเดิมในตาราง
- ปุ่ม/สถานะกลับมาพร้อมให้ retry หลัง error
- เมื่อ retry สำเร็จ UI แสดง timetable จาก response สำเร็จ
