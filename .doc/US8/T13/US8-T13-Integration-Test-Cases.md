## 1. ขอบเขตและแนวทางการทดสอบ
Integration Test ระหว่าง UI กับ API ตรวจการทำงานร่วมกัน 3 ชั้นต่อกันในทุก test case:

1. สิ่งที่ UI ส่ง (HTTP method, path, query parameters, request body, header `Authorization: Bearer <token>`)

2. สิ่งที่ API ตอบ (HTTP status code, JSON body หรือ `ProblemDetail`)

3. สิ่งที่ UI แสดงผล (รายการวิชาที่จะเพิ่ม, รายการวิชาที่ข้ามพร้อมเหตุผล, ข้อความ Empty State, Loading, ข้อความ Error, และตารางเรียนหลังยืนยัน)

กลุ่มทดสอบหลัก 3 กลุ่มตามที่ได้รับมอบหมาย:

- กลุ่ม A — หน้าเว็บเรียก API ดูสรุปแล้วยืนยัน (`dryRun: true` แล้ว `dryRun: false`)

- กลุ่ม B — ยืนยันโดยมีบางวิชาที่เพิ่มไม่ได้ (วิชาที่ข้ามอยู่ใน `skipped` ส่วนวิชาอื่นยังถูกเพิ่ม ไม่ fail ทั้งชุด)

- กลุ่ม C — API ตอบ error แล้วหน้าเว็บแสดงข้อความถูกต้อง

### Endpoints ที่หน้าเว็บเรียก
| ลำดับ | Method & Path | จุดที่หน้าเว็บเรียกใช้ | Test Cases |
| --- | --- | --- | --- |
| 1 | `GET /api/study-plans?studyYear={1-4}&semester={1-2}` | เลือกชั้นปี / ภาคเรียน เพื่อโหลดแผนการเรียน (`plans`) และวิชาโท (`minors`) | `IT-US8-01` – `IT-US8-05`, `IT-US8-27` – `IT-US8-29`, `IT-US8-31` |
| 2 | `POST /api/timetable/apply-plan` (`dryRun: true`) | ดูรายการวิชาที่จะลงตารางก่อนบันทึก | `IT-US8-06` – `IT-US8-15`, `IT-US8-22`, `IT-US8-23` – `IT-US8-26`, `IT-US8-30`, `IT-US8-32` |
| 3 | `POST /api/timetable/apply-plan` (`dryRun: false`) | ปุ่ม "ยืนยันจัดตาราง" | `IT-US8-16` – `IT-US8-22`, `IT-US8-30`, `IT-US8-33` |

หมายเหตุ: ตามการออกแบบใน Spec หลัง `dryRun: false` UI ใช้ `timetable` ใน response วาดตารางต่อได้เลย ไม่เรียก `GET /api/timetable` (US1) ซ้ำ ดังนั้น `GET /api/timetable` อยู่นอกขอบเขตของ T13 แต่ใช้เป็นเครื่องมือตรวจผลใน test (ตรวจว่า `dryRun` ไม่เขียน DB และตรวจว่าวิชาถูกบันทึกจริง)

### สภาพแวดล้อม
- รัน frontend (Next.js) จริง ชี้ไปยัง backend (Spring Boot) และฐานข้อมูล SQL Server จริงที่มี seed ของ US1, US3 และ US8 (preset แผนการเรียน / วิชาโท)

- เข้าสู่ระบบด้วย JWT จริงผ่าน `Authorization: Bearer <token>` (US3)

- ตรวจ Network request/response ผ่าน Playwright หรือ DevTools tab Network

- กรณี Error ที่ไม่เกิดจากการกด UI ปกติ (400, 401, 404 ของ `planId`/`minorId`, 500, Offline) ใช้การดัก/จำลอง response (เช่น Playwright `page.route`) ส่วนกรณีที่ต้องการตรวจ contract ของ API ล้วน ๆ ให้ยิง request ตรงด้วยเครื่องมือ HTTP
